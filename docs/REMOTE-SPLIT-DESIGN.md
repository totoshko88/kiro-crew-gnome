# Design: закриття зауважень ревʼювера щодо curl/sudo/ssh (пункти 2, 3, 4, 7)

Статус: чернетка на затвердження. Гілка `0.1.6`. Автор правок: узгоджується з Anton (totoshko88).

Цей документ фіксує стратегію для найважчої групи зауважень ревʼювера JustPerfection, перш ніж писати код. Пункти 1 і 6 (косметика з module-scope константами) вже зроблено окремими комітами й тут не розглядаються.

## 1. Що вимагає ревʼювер

- (2) Не запускати `curl` з розширення (`lib/profiles.js:89`). Треба `Soup`.
- (3) Розширення не може підіймати привілеї через `sudo` (`lib/profiles.js:96,98`).
- (4) Розширення не може запускати `ssh` (`lib/profiles.js:107,189`; реально процеси спавняться в `lib/remote.js:35` і `shell/tunnel.js:102`).
- (7) Винести цю логіку з пакета розширення в окремий застосунок-залежність, що спілкується через D-Bus. Посилання: гайд GJS по D-Bus, та best-practices правила EGO.

Пункти 2, 3, 4 — це симптоми пункту 7. Правила GNOME Extensions забороняють розширенню запускати довільні зовнішні процеси, підіймати привілеї та відкривати мережеві зʼєднання до сторонніх хостів. Весь цей код у нас зосереджений навколо SSH-керування віддаленими gateway.

## 2. Ключовий висновок дослідження (чому D-Bus-демон НЕ потрібен)

Дослідження поточного Kiro Crew gateway (джерела наведені в кінці) показує, що gateway вже робить нативно саме те, заради чого розширення тримало власний SSH-код:

- Віддалені машини конфігуруються у самому дашборді: Settings → Remote Crew → Add remote crew, з вибором методу (SSH tunnel або AWS SSM). Розширенню не треба власної моделі профілів для віддалених хостів.
- Тунель відкриває сам gateway. Його tunnel manager тримає по одному дочірньому процесу на підключений інстанс і будує або `ssh -N -L`, або `aws ssm start-session`, пробрасуючи loopback-порт. Користувачу не треба руками запускати `ssh` після того, як запис зареєстровано.
- Є локальний HTTP API на loopback-порту gateway, з яким розширення вже вміє говорити (той самий `GatewayClient`): реєстрація через `POST /api/instances`, cloud-launch через `GET /api/cloud/provisioners` і `POST /api/cloud/launch`. Статус віддалених крю дашборд уже показує (Online / Reconnecting / Error / Offline).
- Для речей, які за своєю природою виконуються на хості (автентифікація машини, мінт sign-in URL, провізіонінг нової cloud-машини), існують host-команди: `kirocrew token`, `kirocrew cloud login/logout/launch`, `kirocrew setup`, `kirocrew doctor`, `kirocrew config set ...`.

Наслідок: **розширенню не треба будувати великий host-app + D-Bus-демон для SSH.** Замість переносу SSH-логіки в окремий процес ми її **видаляємо**, бо її роботу вже виконує gateway. Те, що лишається на хості (автентифікація, провізіонінг), ми не автоматизуємо за користувача — показуємо як підказку з готовою командою, як і просив Anton.

Це і є правильне прочитання пункту 7: "винести логіку з розширення" тут означає "віддати її gateway, який і є тим застосунком-залежністю", а не написати свій власний демон.

## 3. Цільова архітектура

Межа дуже проста й повністю відповідає best-practices EGO:

- Розширення спілкується ТІЛЬКИ з локальним gateway на `127.0.0.1:<port>` через `Soup` (HTTP + WebSocket). Це вже наявний транспорт `shell/client.js` / `GatewayClient`. Жодних `Gio.Subprocess`, `ssh`, `sudo`, `curl`.
- Віддалені gateway перестають бути поняттям розширення. Якщо користувач хоче віддалену машину, він додає її в дашборді (Settings → Remote Crew), а розширення показує її статус тим самим каналом, що й локальні слоти.
- Все, що мусить статися на хості (мінт токена локально, керування сервісом, автентифікація, провізіонінг), перетворюється на **підказку-команду**: розширення показує текст команди і кнопку "Скопіювати" (патерн, який уже є для update через clipboard), а не виконує її.

### Що видаляємо з пакета розширення

| Елемент | Файл | Доля |
|---|---|---|
| SSH-тунель | `shell/tunnel.js` (увесь `SshTunnel`) | видалити |
| SSH-контроль віддаленого хоста | `lib/remote.js` (увесь `RemoteControl`) | видалити |
| `remoteCommand()` з `curl`/`sudo`/`systemctl` | `lib/profiles.js:83-102` | видалити |
| `sshCommandArgv()` | `lib/profiles.js:105` | видалити |
| `sshArgv()` | `lib/profiles.js:187` | видалити |
| `usesTunnel`/`usesSshControl`/`sshcontrol` поле | `lib/profiles.js` | видалити або звести до нуля |
| `remote` kind профілю, tunnel-порти, `pickTunnelPort`, `reservedPorts` | `lib/profiles.js` | видалити |
| Споживачі SSH у shell | `shell/connection.js`, `shell/lifecycle.js`, `shell/updates.js` | спростити до local-only |
| Споживачі SSH у prefs | `prefs/profiles.js` | прибрати remote/ssh UI; лишити локальний endpoint + host-підказки |

### Що лишається

- `shell/client.js` (`GatewayClient`) — HTTP/WS до локального gateway. Без змін по суті.
- `lib/localBootstrap.js` — мінт токена через owner-only unix-сокет (локально, без мережі до чужого хоста, без sudo). Це легітимно, бо спілкування йде з локальним gateway цього ж користувача. Залишаємо.
- Локальний профіль/endpoint (порт gateway) — лишається; віддалені прибираються.
- Підказки-команди (`kirocrew token`, `kirocrew doctor`, Remote Crew в дашборді) — новий невеликий UI замість SSH-автоматики.

## 4. Залишкові питання для рішення (потрібне твоє "так")

Є три розвилки, де варіант впливає на обсяг і UX. Пропоную дефолти, але хочу підтвердження.

A. Доля prefs-UI "віддалені профілі". Варіанти:
   - A1 (рекомендовано): прибрати додавання віддалених профілів зовсім; у prefs лишити тільки локальний порт + панель "Віддалені машини тепер керуються в дашборді Kiro Crew → Settings → Remote Crew" з кнопкою, що показує/копіює крок. Мінімум коду, максимально у дусі ревʼювера.
   - A2: лишити список віддалених як read-only відображення того, що повертає gateway (`/api/instances`), без можливості керувати SSH. Більше коду, але показує віддалені крю в топ-барі.

B. Статус віддалених крю в топ-барі. Чи хочемо ми у 0.1.6 вже показувати Online/Reconnecting/Error/Offline віддалених крю (дані бере gateway), чи це окремий майбутній реліз? Показ статусу читається з наявного WS-каналу, ризик низький, але це додаткова робота. Дефолт: винести в наступний реліз, 0.1.6 робить лише видалення SSH + підказки.

C. Міграція наявних користувачів. У дехто вже збережені remote-профілі в gsettings (schema має ці ключі). Варіанти:
   - C1 (рекомендовано): при старті, якщо є збережені remote-профілі, показати одноразову нотифікацію "віддалені профілі більше не керуються розширенням; додай їх у Kiro Crew → Settings → Remote Crew" і тихо прибрати їх зі стану. Нічого руйнівного.
   - C2: лишити ключі в схемі, просто ігнорувати. Менше коду, але схема тягне мертві ключі.

## 5. План робіт (після затвердження), окремий коміт на пункт

1. `Soup` замість `curl` — технічно зникає разом із видаленням `remoteCommand`, тож пункт 2 закривається видаленням, а не переписуванням. (Якщо десь лишиться локальний HTTP — він уже на `Soup`.)
2. Видалити `shell/tunnel.js` + споживачів → закриває частину пункту 4.
3. Видалити `lib/remote.js` + споживачів → закриває пункт 3 (sudo) і решту пункту 4 (ssh-контроль).
4. Вичистити `lib/profiles.js` від ssh/tunnel/remoteCommand → закриває пункт 2 остаточно.
5. Спростити `prefs/profiles.js` до local-only + підказки (рішення A).
6. Міграція/нотифікація для старих профілів (рішення C).
7. Оновити `metadata.json` опис (прибрати згадку SSH-тунелю й "runs the ssh command"), README, USERGUIDE, schema.
8. Оновити тести `tests/test-profiles.js` (прибрати ssh/tunnel кейси).

Кожен крок — окремий фокусний коміт. Наприкінці — зведений сценарій ручної перевірки (включно з on-device запуском бінаря, бо зміни торкаються prefs/連connection-UI, а зелений gate не ловить SIGSEGV при realize).
